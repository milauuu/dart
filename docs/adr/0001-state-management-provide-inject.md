# ADR-0001: State management via provide/inject

**Context:** `Home.vue` needs access to both `matches` and `activeMatch`. `MatchView.vue` and `MatchPlayerCard.vue` only need `activeMatch`. `MatchFinishModal.vue` needs neither — it receives derived values (`winner-name`, `is-last-player`) as regular props from `MatchView.vue`. Without a shared mechanism, `matches`/`activeMatch` would need to be passed down manually through props, or duplicated locally — both error-prone as the component tree grows.

**Options considered:**
1. Prop drilling — pass `matches` and `activeMatch` down explicitly through every intermediate component.
2. A dedicated state management library (e.g. Pinia) — a centralized store outside the component tree.
3. Vue's built-in `provide`/`inject` — `App.vue` provides the state once, any descendant injects it directly.

**Decision:** Option 3 — `provide`/`inject`, with `App.vue` as the single source of truth for both `matches` and `activeMatch`.

**Rationale:** The app is small and single-user, client-only, with no server-side state to synchronize — the overhead of a dedicated store (Pinia) isn't justified for this scale. Of the remaining options, `provide`/`inject` was chosen because `App.vue` can provide the state once, and any descendant that genuinely needs it injects it directly, without relay logic through components that don't use it themselves. Components without a genuine need for `matches`/`activeMatch` (e.g. `MatchFinishModal.vue`) receive derived values via props instead of injecting — injection is reserved for components that need direct access to the shared state itself.

**Known limitation:** `activeMatch` holds a direct reference into `matches`, and this is relied on throughout normal operation — `MatchView.vue` and `MatchPlayerCard.vue` mutate fields directly on `activeMatch.value` (e.g. `status`, `currentPlayerIndex`), which updates the corresponding `matches` entry in place without ever reassigning `matches.value` itself. This also means: if a match were deleted from `matches` while active, `activeMatch` would be left pointing to an orphaned object. No such deletion path currently exists — the delete action is only reachable from `Home.vue`, which isn't rendered while a match is active — so this is a UI-enforced invariant, not a structural guarantee. Accepted as low risk at current scope; noted here to avoid re-diagnosing it from scratch if the deletion or navigation flow changes. Separately, `inject()` returns a plain `ref` with no protection against local reassignment — nothing prevents a component from creating a local copy (e.g. `const local = ref(injectedRef.value)`) that silently diverges from the SSOT. `inject()` also provides no compile-time guarantee that a matching `provide()` exists upstream; a missing provide surfaces as `undefined` at the point of use, not at the injection site.

**Trade-off accepted:** `provide`/`inject` gives up traceability compared to prop drilling: a component further down the tree can inject the state without any visible link to where it originates, making the dependency harder to spot by reading the component tree alone. This compounds the reassignment risk noted above — a diverging local copy is also harder to trace back to its source than it would be with an explicitly passed prop. These are reasonable trade-offs for a small, single-developer codebase — the team is small enough to reliably track where and how the SSOT is mutated without either the guardrails from props or a dedicated store like Pinia. The avoided boilerplate — not having to relay `matches`/`activeMatch` through intermediate components that don't use them themselves — was the deciding factor in favor of `provide`/`inject` at this scale; it would need tightening (e.g. Pinia) in a larger team.
